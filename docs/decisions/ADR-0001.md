# ADR-0001: Lenguaje y runtime

## Estado
Aceptado.

## Contexto y problema
El equipo necesita fijar desde el inicio el lenguaje y el entorno de ejecución sobre los que se construirá todo el sistema (gestor de trabajos, CLI, mecanismos de concurrencia y persistencia), de forma que el resto de las decisiones de arquitectura (ADR-0002, ADR-0003) puedan apoyarse en una base común.

## Alternativas consideradas
### Opción A — Python 3
* **Ventaja:** Biblioteca estándar suficiente para procesos (`subprocess`), concurrencia (`threading`/`queue`) y manejo de archivos; curva de aprendizaje baja para todo el equipo; facilidad para escribir pruebas (`unittest`) y scripts de verificación.
* **Riesgo:** Rendimiento menor que alternativas compiladas para cargas muy altas, no relevante para el alcance del curso.

### Opción B — Bash puro
Descartada: Manejar estructuras de datos (registro de trabajos, estados, filtros) y concurrencia de forma robusta en Bash es frágil y dificulta las pruebas automatizadas.

## Decisión
Python 3.

## Consecuencias
* **Positivas:** Biblioteca estándar cubre procesos, hilos y E/S sin dependencias adicionales; todo el equipo puede contribuir sin curva de aprendizaje adicional.
* **Negativas / riesgos:** Hay que vigilar el uso correcto del GIL al diseñar la concurrencia (relacionado con ADR-0002).

## Requisitos afectados
Transversal a todos los RF/RNF del proyecto.

## Evidencia / prototipo
El ADR original referencia `src/job_manager.py`, `src/cli.py`, `tests/test_job_manager.py` y `verif/scripts/run_tests.sh` como evidencia.
