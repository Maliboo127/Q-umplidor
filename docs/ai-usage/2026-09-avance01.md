# Registro de uso de IA — Avance 01 (núcleo local)

Formato por entrada: objetivo, resultado recibido, revisión realizada,
cambios aplicados, prueba agregada, aprendizaje.

---

## Entrada 1 — Núcleo del JobManager (resultado ACEPTADO tras verificación)

**Objetivo:** Implementar el gestor de trabajos (cola, concurrencia,
ejecución como proceso separado, estados, cancelación, captura de
stdout/stderr) para el Hito 1.

**Resultado recibido:** Código completo de `job_manager.py`, `cli.py` y
`main.py` con un pool de hilos trabajadores consumiendo una cola
thread-safe, lanzando cada trabajo con `subprocess.Popen`.

**Revisión realizada:** Se corrió el código y se le escribieron 12 pruebas
unitarias automatizadas cubriendo envío, estados, cancelación (en cola y
en ejecución), captura separada de stdout/stderr, comando inválido, y
respeto del límite de concurrencia. Las 12 pruebas pasaron en el entorno
de referencia.

**Cambios aplicados:** Ninguno al código en sí — se aceptó tal cual tras
pasar las pruebas.

**Prueba agregada:** `tests/test_job_manager.py` completo (12 casos).

**Aprendizaje:** Un pool fijo de hilos + `queue.Queue` es suficiente para
garantizar el límite de concurrencia de forma estructural, sin necesitar
un semáforo adicional.

## Entrada 2 — Portabilidad de las pruebas (resultado MODIFICADO por deficiencia)

**Objetivo:** Verificar que las 12 pruebas unitarias también pasaran en
la máquina de desarrollo de un integrante del equipo (Windows), no solo
en el entorno donde se escribieron originalmente.

**Resultado recibido:** Las pruebas usaban comandos como `true`, `false`,
`sleep` y `echo` como comandos de prueba genéricos.

**Deficiencia encontrada:** Al correr `python -m pytest tests\ -v` en
Windows, **5 de 12 pruebas fallaron** — `true.exe`, `false.exe` y
`sleep.exe` no existen como ejecutables reales en Windows (son binarios de
coreutils de Unix/Linux), y `echo` tampoco es un ejecutable independiente
en Windows (es un comando interno de `cmd.exe`). `subprocess.Popen` no
pudo encontrarlos y todos los trabajos de prueba cayeron en `FAILED` por
"comando no encontrado", incluso los que debían pasar.

**Cambios aplicados:** Se reemplazaron todos los comandos de prueba por
invocaciones al propio intérprete de Python (`sys.executable` + `-c
"código corto"`), que sí existe de forma idéntica en Windows y Linux. Se
corrigió en dos rondas porque la primera corrección dejó sin reemplazar
4 usos de `echo` que se pasaron por alto en la revisión inicial.

**Prueba agregada:** Las mismas 12 pruebas, ahora reescritas de forma
portable; se re-ejecutaron en Windows hasta confirmar `12 passed`.

**Aprendizaje:** El sistema final debe apuntar a Linux (RNF-01), pero el
equipo desarrolla en máquinas con distintos sistemas operativos. Las
pruebas automatizadas deben evitar depender de binarios específicos del
SO de desarrollo; usar el propio intérprete de Python como comando de
prueba es portable y no cambia lo que se está probando (el manejo de
procesos, no el comando en sí). Este incidente quedó documentado también
como aprendizaje de equipo para futuras pruebas.

## Entrada 3 — Propuesta de daemon con socket TCP (resultado RECHAZADO)

**Objetivo:** Resolver la limitación de que cada invocación del CLI crea
un `JobManager` nuevo sin memoria compartida entre invocaciones.

**Resultado recibido:** Una propuesta inicial de implementar ya un daemon
persistente con un socket TCP escuchando en una interfaz de red, para que
el CLI pudiera hablar con un servicio en segundo plano.

**Motivo de rechazo:** El Hito 1 (doc. 06) dice explícitamente "no se
requiere todavía la operación remota", y el acceso remoto tiene requisitos
propios de seguridad (RF-20, RNF-12, RNF-13: restricción a LAN/VPN) que no
se habían diseñado ni revisado todavía. Adelantar un socket de red en esta
etapa habría introducido superficie de ataque sin las validaciones
correspondientes, y se habría solapado con el trabajo planeado para el
Hito 3. Se descartó la propuesta y se documentó la limitación de forma
explícita en el código (`src/main.py`) en vez de resolverla
prematuramente.

**Aprendizaje:** No toda limitación conocida debe resolverse de inmediato;
a veces la decisión correcta es documentarla y posponerla al hito que le
corresponde, en vez de aceptar una solución generada por IA solo porque
funciona técnicamente.
